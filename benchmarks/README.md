# Бенчмарки векторных хранилищ: FAISS vs ChromaDB vs Qdrant, эмбеддинги bge-m3

*Замеры проводил на своей машине. Замер Qdrant сделал в **локальном режиме** qdrant-client. Он не строит HNSW-граф и потому ищет полным перебором. В целом, для реальных задач лучше смотреть официальные бенчмарки.*

## Окружение

- CPU (без GPU), Python 3.14
- faiss 1.15.1, chromadb 1.5.9, qdrant-client 1.19.1 (локальный режим)
- sentence-transformers, модель BAAI/bge-m3 (1024-dim)

## Структура

- `common.py` -- общий модуль: генерация базы знаний, чанкинг, эмбеддинги с кэшированием, замер времени.
- `generate_knowledge_base.py` -- создаёт 30 синтетических документов (детерминированно, seed 42; один файл -- одна сущность).
- `benchmark_faiss.py`, `benchmark_chromadb.py`, `benchmark_qdrant.py` -- по одному скрипту на векторную базу; каждый печатает замеры и JSON.

## Как запустить

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python generate_knowledge_base.py   # 30 документов в knowledge_base/
python benchmark_faiss.py           # замер FAISS
python benchmark_chromadb.py        # замер ChromaDB
python benchmark_qdrant.py          # замер Qdrant (локальный режим)
```

Первый запуск скачивает модель bge-m3 (~2.3 ГБ). Эмбеддинги кэшируются в `embeddings_cache.npy`, повторные запуски идут быстро.

## Методика

1. База знаний: 30 синтетических документов, генерируются скриптом.
2. Чанкинг: ~400 слов на чанк, перекрытие 60 слов -> 90 чанков.
3. Эмбеддинги: bge-m3, нормализованные, одинаковые для всех трёх баз -- сравниваются базы, а не их встроенные эмбеддеры.
4. Для каждой базы: время построения индекса, латентность поиска top-5 (среднее по 20 запросам), размер хранилища.
5. Масштабный тест: готовые эмбеддинги размножаются до ~10 000 векторов с крошечным шумом. Время эмбеддинга не зависит от базы, поэтому размножение изолирует слой хранилища.
6. Валидация: все базы должны вернуть одинаковый корректный top-1 документ на тестовый запрос.

## Результаты

### Эмбеддинги: bge-m3 на CPU

| Метрика | Значение |
| --- | --- |
| Загрузка модели (из кэша / первый запуск) | 10 с / ~393 с |
| Скорость эмбеддинга | 0.43 чанка/с (90 чанков за ~203 с) |
| Экстраполяция на ~100k чанков (боевой датасет) | ~64 часов на CPU |

Вывод: для учебного датасета (90 чанков) CPU достаточен. Для боевого датасета лучше арендовать GPU на несколько часов.

### Хранилища (одинаковые векторы bge-m3, top-5)

| Метрика | FAISS (IndexFlatIP) | ChromaDB 1.5.9 (HNSW) | Qdrant 1.19.1 (локальный режим) |
| --- | --- | --- | --- |
| Построение, 90 векторов | 0.3 мс | 137.9 мс | 35.2 мс |
| Построение, 9 990 векторов | 6.6 мс | 1 322 мс | 4 196 мс |
| Поиск top-5, 90 векторов | 0.030 мс | 0.874 мс | 0.495 мс |
| Поиск top-5, 9 990 векторов | 1.563 мс | 0.834 мс | 18.558 мс |
| Хранилище, 90 векторов | 360 КиБ (index) | 2 866 КиБ | в памяти |
| Загрузка с диска | 0.4 мс | (постоянный сервер) | не применимо |

Валидация: все три базы вернули одинаковый корректный top-1 документ (`20_hyperrelay_incident_postmortem.md`) на запрос "Who owns HyperRelay and what dashboard should I check first?".

## Выводы

На масштабе учебного датасета все базы мгновенны. Всё решает вызов LLM. Выбран FAISS (скорость индексации, компактность, простая реализация бота).
